# mcMPP NPP API 全量实现开发计划

> 状态：v1（2026-10-28）
> 基线：`dev` @ `3a81f00`
> 集成分支：`feat/npp-api-expansion`
> 参考实现：NVIDIA NPP 13.4（5090，CUDA 13.4），公共契约头文件：`API/`（API-unified）

## 1. 目标与范围

### 1.1 目标

以 `API/`（`API-unified`）中的函数声明为唯一公共契约，把 mcMPP 从当前的部分实现推进到**全量 API 覆盖**：

- 每个 `API/` 中声明的 `nppi*` / `npps*` 函数都有真实实现（不是 `NPP_NOT_IMPLEMENTED_ERROR` 占位）。
- 每个函数在 `_Ctx` 入口上以 NVIDIA NPP 13.4 为功能基线完成 5090 交叉验证。
- 非 `_Ctx` 入口通过统一的 Adapter 转发到 `_Ctx`，行为与 `_Ctx` 一致。
- 覆盖率、测试状态、验证记录可重复生成、可审计。

### 1.3 明确不在本期范围

- 以性能为首要目标的优化（先正确性、后性能；核心家族在正确性稳定后单独做 benchmark 包）。
- NPP 13 相比 API-unified 新增、且 `API/` 中不存在的私有/新版接口。
- `size_t` 重载的独立实现：API-unified 在 C++ 模式下同时声明 `int` 与 `size_t` 两个重载；本期实现以外交 C 的 `int` 版本为准，`size_t` 兼容重载在 P7 统一评估。
- 对既有公共 API 语义的破坏性变更。

## 2. 现状问题与度量修正

1. **覆盖率工具把 stub 当作实现**：`tools/check_coverage.py` 只匹配函数定义，无法区分真实实现和 `return NPP_NOT_IMPLEMENTED_ERROR;`。166 个 stub 被高估为实现。
2. **覆盖口径与公共头文件不一致**：coverage 使用 `api_analysis/api_functions_12.2.csv`，而构建和安装使用 `API/`（API-unified）。二者唯一函数名相差 37/46 个，需以 `API/` 为准重新生成 catalog。
3. **NPPS 测试未编译**：`test/unit/CMakeLists.txt` 中 `npps/test_*.cpp` 被注释掉（12.8 的 `int`/`size_t` malloc 差异）。NPPS 有 1,728 个待实现函数，测试必须先恢复。
4. **测试判定过于宽松**：测试扫描只检查函数名是否在测试文件中出现，不能区分“真正调用并断言”与“仅作为字符串/转发出现”。
5. **NPP 13 移除了非 `_Ctx` 符号**：`build-nvidia` 只能链接 `_Ctx` 入口；非 `_Ctx` 正确性需通过“同 golden、不同入口”的对照测试证明。
6. **NPP 13 的 `nLength` 为 `size_t`**：测试与生成代码必须通过 `NppSignalLength`/`SIZE_TYPE` 兼容层处理，不能把类型写死。

## 3. 总体架构与设计模式

### 3.1 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ 1. API Surface（生成）                                        │
│    nppiXxx_8u_C1R / ..._Ctx：精确签名、extern "C"、C ABI        │
│    non-Ctx = Adapter → _Ctx(nppCreateDefaultStreamContext())  │
├──────────────────────────────────────────────────────────────┤
│ 2. Family Facade / Executor（每家族手写 + 模板）               │
│    参数校验 → ROI/step 语义 → workspace → launch → error check │
├──────────────────────────────────────────────────────────────┤
│ 3. Algorithm Strategies（Policy / Strategy）                   │
│    dtype policy、channel/layout policy、border policy、        │
│    interpolation strategy、reduction strategy、error metric    │
├──────────────────────────────────────────────────────────────┤
│ 4. Kernels（模板 kernel）                                      │
│    1D/2D 通用循环、逐像素/归约/滤波/几何 kernel                │
├──────────────────────────────────────────────────────────────┤
│ 5. Runtime Services                                           │
│    stream context、device buffer RAII、error mapping、         │
│    buffer-size registry、device props                         │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 设计模式与取舍

| 模式 | 落点 | 原因 |
|---|---|---|
| **Facade** | 每个 API family 一个 `namespace nppi::<module>::<family>` | 把 9,000 个入口收敛到约 120 个家族实现 |
| **Adapter** | 生成的非 `_Ctx` 入口 → `_Ctx` | 消除 4,500 个手工重复入口 |
| **Template Method** | `Executor::run()` 固定“校验→工作区→launch→错误检查”骨架 | 所有家族共享一致的状态码/ROI 语义 |
| **Policy-Based Templates** | `DTypePolicy<T>`、`ChannelPolicy<C>`、`BorderPolicy<B>` | 编译期分派，避免运行时 switch 和宏 |
| **Strategy + Registry** | 插值、边界模式、范数类型、误差度量 | 算法可变、接口稳定；buffer-size 查询按策略注册 |
| **RAII** | `DeviceBuffer` / `ScratchWorkspace` | 杜绝 scratch buffer 泄漏，异常安全 |
| **Data-Driven Generation** | catalog + family manifest → wrappers/tests | 4,500 个入口不可能手写；生成物可复现、可审计 |
| **Differential Golden Testing** | 5090 record / MACA verify | 以真实 NPP 输出为基线，覆盖全部变体 |
| **Object Mother / Test Data Builder** | 测试数据构造器 | 统一确定性输入、ROI/pitch/边界用例 |

约束：

- 沿用仓库现有风格：`nppi_arithmetic_operations` 的模板 + `Executor` 模式是范本；**不引入宏生成框架**（算术模块明确使用纯 C++ 模板）。
- 新代码优先落到现有模块目录；公共组件放 `src/include/`，不另起平行体系。
- 生成文件加 `// GENERATED by mpp_scripts/gen_family.py -- DO NOT EDIT` 头；手写 executor 与生成 wrapper 分离。
- 所有新 `_Ctx` 入口必须使用 `nppStreamCtx.hStream`，非 `_Ctx` 使用 `nppCreateDefaultStreamContext()`。

### 3.3 新增公共组件

| 文件 | 内容 |
|---|---|
| `src/include/npp_type_traits.h` | dtype traits：`NppTypeTraits<T>`（min/max、饱和、累加类型、`IsFloat`）；16f/复数支持 |
| `src/include/npp_channel_traits.h` | `ChannelPolicy<C>`：packed/AC4/planar 的索引与 alpha 规则 |
| `src/include/npp_executor.h` | `run2D()`/`run1D()`：grid/block、边界检查、`cudaGetLastError()`、空 ROI 语义 |
| `src/include/npp_buffer.h` | `DeviceBuffer`（RAII）、`GetBufferHostSizeRegistry` |
| `src/include/npp_border_policy.h` | `BorderPolicy<REPLICATE/WRAP/CONSTANT/REFLECT>` |
| `src/include/npp_interpolation.h` | nearest/linear/cubic 的采样策略（复用几何模块现有实现） |

### 3.4 代码生成

新增两个工具：

1. **`tools/npp_api_catalog.py`**（P0.1）
   - 解析 `API/` 头文件，保留参数名与原始签名；
   - 生成 `api_analysis/api_catalog.csv`：`function, module, family, dtype, channels, layout, inplace, ctx, return_type, params, signature`；
   - 扫描 `src/`，区分 `real` / `stub` / `missing`；扫描 `test/` 记录 `tested`；
   - 生成 `api_analysis/backlog.csv`（按 package/family 汇总）与 `coverage_summary.md`；
   - 替换 `check_coverage.py` 的统计口径（保留旧脚本兼容入口）。

2. **`mpp_scripts/gen_family.py`**（P0.4）
   - 输入：`mpp_scripts/families/<family>.json` + catalog；
   - 输出：
     - `src/.../<family>_generated.cpp`：`_Ctx` 入口调用家族 executor；非 `_Ctx` 入口转发；
     - `test/unit/.../test_<family>_generated.cpp`：参数化差分测试骨架；
   - family spec 字段示例：

```json
{
  "family": "nppsSum",
  "module": "npps_statistics_functions.h",
  "executor": "nppi::statistics::npps_sum",
  "call": "nppi::statistics::npps_sum::run<{dtype}>({pSrc}, {nLength}, {pSum}, {pDeviceBuffer}, nppStreamCtx.hStream)",
  "ctx_only": false,
  "tolerance": {"int": 0, "float": 1e-6},
  "record_cases": ["sum_1x17", "sum_aligned", "sum_zero"]
}
```

   - 生成器只处理“同一 family 内仅 dtype/channel/ROI 变化”的规则变体；签名不规则的函数由 family executor 手写 wrapper，spec 中用 `manual: true` 标记。
   - 生成物与手写物同名冲突检测：若 catalog 中函数已有真实定义则跳过并报错。

### 3.5 测试架构

`test/unit/framework/npp_diff_harness.h`：

- **Case 声明**：`NppDiffCase{ id, function, roi, steps, dtype, channels, inputs, outputs, status }`。
- **确定性数据**：case id 作为种子；边界值（0、1、min、max、NaN/Inf for float）单独 case。
- **Record 模式**（仅在 5090 + NVIDIA NPP 构建）：`--npp-record=<dir>`，把 status + 输出 buffer 写成紧凑二进制 + JSON manifest。
- **Verify 模式**（本地 MPP 构建）：`--npp-verify=<dir>`，逐 case 比较 status 与输出；整数精确，浮点按 family 容差（默认 `rtol=1e-5, atol=1e-5`，滤波/几何可配）。
- **入口适配**：`build-nvidia` 只调用 `_Ctx`；MPP 侧同时调用 `_Ctx` 与非 `_Ctx`，两者都与同一 golden 比较。
- **Contract 测试**：统一覆盖空 ROI（`NPP_NO_ERROR`）、负尺寸（`NPP_SIZE_ERROR`）、空指针（`NPP_NULL_POINTER_ERROR`）、步长不足（`NPP_STRIDE_ERROR`）、NPP 13 状态码差异白名单。
- **Golden 存储**：`test/golden/diff/<module>/<family>/<case>.bin`；仅存小尺寸规范用例（≤ 64×64），单家族控制在几十 KB。
- **跳过清单**：NPP 13.4 不导出/行为不可比的函数记录在 `test/unit/framework/npp_diff_skip.json`，并在报告中列明原因。

## 6. 子 Agent 协作流程

### 6.1 角色

- **主 agent（Lead）**：维护计划、审查/合并、全量回归、进度账本、风险处理。
- **工作包 agent**：每个 P* 包一个，独立 worktree，按 DoD 完成实现、测试、5090 验证、提交。

### 6.2 执行流程

1. Lead 从集成分支创建 `pkg/<id>` 分支与 worktree：`git worktree add /home/cjxu/worktrees/mcMPP-<id> -b pkg/<id> feat/npp-api-expansion`。
2. Lead 写 `docs/agent_packages/<id>.md`（范围、家族清单、参考实现、验收命令、已知风险）。
3. 启动 agent：

```bash
cd /home/cjxu/worktrees/mcMPP-<id>
export ANTHROPIC_BASE_URL="https://llm-gw.kai.metax-tech.com"
export ANTHROPIC_AUTH_TOKEN="<gateway-token>"
export ANTHROPIC_MODEL="deepseek-v4-flash"
export CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000
claude -p --permission-mode bypassPermissions \
  --append-system-prompt "你是 mcMPP 的 NPP API 实现子 agent..." \
  "$(cat docs/agent_packages/<id>.md)"
```

4. Agent 完成后：Lead 检查 `git log/diff`，运行 A/B/C 验证与覆盖率，`git merge --no-ff pkg/<id>` 到集成分支。
5. 更新 `docs/npp_api_progress.md` 与 `api_analysis/backlog.csv` 状态，再启动下一个包。

### 6.3 Agent 行为约束（写入每个 prompt）

- 先读 `docs/npp_api_expansion_plan.md`、`docs/mpp_api_implementation_guide.md`、`docs/agent_packages/<id>.md`。
- **测试先行**；先在 5090 证明测试成立，再改 `src/`。
- 只改本包范围内的文件；公共组件改动必须先报告 Lead。
- 不 push Gerrit、不 force push、不删测试、不做性能优化、不修改 build 目录。
- 复用现有 executor/template；禁止为单个函数复制整套实现。
- 提交粒度：一个家族一个 commit；提交信息 `[mcMPP] <module>: implement <family> ...`。
- 结束报告：覆盖函数数、文件、5090/A/B/C 结果、未覆盖项、后续风险。

### 6.4 并发策略

| 风险 | 影响 | 缓解 |
